PART 1

스킬 설계 방법론

좋은 스킬은 우연히 나오지 않는다.
다섯 가지 원칙으로 설계한다.

ANATOMY

스킬은 4가지로 구성된다

🪪

1. Frontmatter

name과 description. 트리거 키워드가 모두 들어가야 Claude가 스킬을 호출한다.

📋

2. 워크플로우

"이 스킬이 호출되면 무엇을 어떤 순서로 실행하는지" 절차를 명문화한다.

📚

3. 참조 자료

references/ 폴더에 디테일 보관. 본문은 짧게, 디테일은 분리.

🛠

4. 스크립트

scripts/ 폴더에 자동화 코드. 결정론적 작업은 LLM이 아니라 코드가 처리.

PRINCIPLE 1

트리거 정확도 = 스킬 생존율

description은 마케팅 문구가 아니다. "어떤 말이 들어오면 이 스킬을 써야 하는지"를 가능한 모든 표현으로 나열하는 매칭 사전이다. 한국어/영어 동의어, 명령형/평서형 모두 포함.

# ❌ 나쁜 description description: 보안을 검토하는 스킬 # ✅ 좋은 description description: 바이브코딩 프로젝트의 배포 전/후 보안 취약점을 검사하고 보완 지침을 제공. Next.js, Supabase, Vercel 스택 대상. "보안 검토해줘", "security audit", "취약점 검사", "배포 전 점검" 등의 요청 시 사용.
PRINCIPLE 2

결정론과 추론을 분리하라

스킬에서 가장 자주 놓치는 부분이다. LLM이 잘하는 일과 코드가 잘하는 일은 다르다.

🧠 LLM이 잘하는 일

  • 맥락 파악, 우선순위 판단
  • 자연어 분석 및 요약
  • 창의적 변형, 어조 조절
  • 다양한 입력 패턴 대응

⚙️ 코드가 잘하는 일

  • 파일 스캔, 패턴 매칭
  • API 호출, DB 쿼리
  • 정확한 수치 계산
  • 매번 같은 결과 보장
PRINCIPLE 3

본문 짧게, 참조 깊게

SKILL.md 본문은 컨텍스트를 항상 차지한다. 모든 디테일을 본문에 넣으면 토큰 낭비. "필요할 때만 읽도록 references/에 분리"하는 것이 핵심 패턴.

📁 my-skill/
📄 SKILL.md ← 짧은 워크플로우만
📁 references/ ← 필요할 때만 view
📄 design-system.md
📄 api-reference.md
📁 scripts/ ← 결정론적 자동화
📄 audit.py
PRINCIPLE 4

하나의 스킬은 하나의 역할만

하나의 스킬이 여러 책임을 가지면 LLM이 "지금 어느 모드인가"를 헷갈리고, 트리거 정확도도 떨어진다. 여러 스킬을 조합하는 편이 항상 낫다.

❌ 책임이 너무 많음

  • code-everything 스킬
  • 리뷰 + 리팩토링 + 배포 + 문서화
  • "어느 부분을 했는지" 모호

✅ 단일 책임

  • code-review 스킬
  • security-audit 스킬
  • doc-generator 스킬
PRINCIPLE 5

검증 가능한 출력을 만들어라

스킬을 에이전트로 옮길 때 가장 큰 문제는 "결과가 좋아졌는지 어떻게 아는가"다. 스킬 단계부터 출력 포맷을 구조화해두면 평가가 자동화된다.

# 출력 포맷을 SKILL.md에 명시 ## 출력 포맷 { "status": "pass | warning | fail", "issues": [ { "severity": "critical|high|medium|low", "category": "auth|db|deps|env", "description": "...", "fix": "..." } ], "summary": "..." }
RECAP

스킬 설계 5원칙

  1. 트리거 정확도
    description에 가능한 모든 표현을 넣는다
  2. 결정론과 추론의 분리
    LLM에는 판단을, 코드에는 계산을
  3. 본문 짧게, 참조 깊게
    references/와 scripts/로 분리
  4. 단일 책임
    하나의 스킬은 하나의 역할만
  5. 검증 가능한 출력
    JSON 등 구조화된 포맷으로 결과 정의

PART 2

스킬 → 에이전트
이식 과정

Claude.ai에서 검증한 스킬을
Vercel + Gemini 위에서 돌리는 에이전트로 옮긴다.

INSIGHT

스킬은 시스템 프롬프트의 원형

SKILL.md를 잘 다듬어두면 그게 거의 그대로 에이전트의 시스템 프롬프트가 된다. Claude.ai는 무료 실험실, 에이전트는 프로덕션. 동일한 두뇌가 두 환경에서 돌아간다.

💡 실용 팁: 메인 API가 Gemini라도 스킬 검증은 Claude.ai에서 하는 게 효율적이다. 검증된 프롬프트를 Gemini용으로 살짝 다듬어서 이식하면 된다.
PROCESS

이식 5단계

  1. 스킬 정의 & Claude.ai에서 100회 이상 호출 검증
    edge case 발견하면 SKILL.md에 반영
  2. SKILL.md를 시스템 프롬프트로 변환
    frontmatter 제거, Gemini용 어조 조정
  3. references/, scripts/를 코드베이스로 포팅
    Vercel Edge Function 안에서 호출 가능하게
  4. Slack Slash Command + Webhook 연결
    트리거 → 에이전트 → 슬랙 리턴 루프 완성
  5. Supabase에 실행 로그 누적
    결과 데이터를 스킬 개선의 input으로 재사용

OVERVIEW

왜 이 3가지인가

🛡️

CASE A
배포 게이트키퍼

기존 security-audit 스킬의 자연스러운 확장. 이미 있는 자산을 활용.

CASE B
리서치 큐레이터

경쟁사·트렌드 모니터링. 외부 데이터 결합 학습 포인트.

부업 아이디어 즉시 검증. 상업화 가능성이 가장 높은 케이스.

CASE A

🛡️ 배포 게이트키퍼
Deployment Gatekeeper

Vercel/AWS 배포 직전에 자동 실행되는 보안 검토 에이전트.
기존 security-audit 스킬을 자동화 루프에 편입.

SKILL DESIGN

스킬은 이미 있다 (security-audit)

당신이 이미 만든 security-audit 스킬이 출발점. 의존성 취약점, Supabase RLS, 환경변수 검사를 담당. 이걸 그대로 가져와서 "GitHub push 이벤트가 발생하면 자동 실행" 하도록 옷만 갈아입힌다.

# SKILL.md → 시스템 프롬프트로 변환되는 부분 ## 검사 항목 1. 의존성 취약점 (package.json + npm audit) 2. Supabase RLS 정책 누락 여부 3. .env 노출 가능성 (커밋 검사) 4. API 라우트의 인증 처리 5. CORS / CSP 헤더 설정 ## 출력 포맷 { status, blocking_issues[], warnings[], summary }

DEEP DIVE

"근데 cron은 뭘로 돌리지?"

CASE B를 만들 때 가장 먼저 부딪히는 결정이 "정기 실행을 무엇으로 돌리느냐"다. 선택지는 셋. 각자 태생이 달라서 가격·신뢰성·복잡도 트레이드오프가 명확하다.

🐧

리눅스 cron

1975년부터의 OS 스케줄러. 항상 켜진 서버가 있어야 한다.

🐙

GitHub Actions

CI/CD 워크플로우 엔진. 스케줄 트리거는 부가 기능.

▲

Vercel Cron

서버리스 함수 위에 얹은 스케줄러. 자체 서버 없음.

COMPARE

정면 비교

항목 리눅스 cron GitHub Actions Vercel Cron
인프라 서버 필요 없음 없음
시간 정확도 매우 정확 5~15분 지연 1~2분 지연
최대 실행 시간 무제한 6시간 Pro 60초
무료 한도 서버비 별도 월 2,000분 Hobby 2개·일 1회
외부 호출 제약 없음 제약 없음 자기 함수만
⚠️ GitHub Actions의 cron은 "best effort". 공식 문서에도 "혼잡할 때 지연·스킵 가능"이라 명시됨.
DECISION GUIDE

상황별 선택 한 줄 가이드

  1. 60초 이내 작업 · 이미 Vercel 사용 중 → Vercel Cron
    RSS 몇 개 + Gemini 한 번 호출 정도. vercel.json에 한 줄 추가로 끝.
  2. 5분 이상 무거운 작업 → GitHub Actions
    경쟁사 30곳 순회·종합 분석. 최대 6시간 가능, 무료 한도 넉넉.
  3. 분 단위 정확한 시간 엄수 → Upstash QStash (별도)
    금융·알림 등 5분 지연도 치명적인 도메인. 부업 수준에선 보통 오버킬.
  4. 외부 서비스만 호출하면 됨 → GitHub Actions
    Vercel 함수를 거칠 필요가 없을 때. Secrets 관리도 깔끔.
HYBRID

CASE B 실전 구성: 둘을 같이 쓴다

한쪽만 고를 필요 없다. 수집은 GitHub Actions, 큐레이션·전송은 Vercel로 역할 분담.

# GitHub Actions (7:30 AM KST, 무거운 수집 작업) on: schedule: - cron: '30 22 * * *' # UTC 기준! jobs: fetch: steps: - run: python scripts/fetch_sources.py - run: curl -X POST $VERCEL_API/api/curator/summarize # Vercel API (가볍고 빠른 추론·전송) export default async function handler(req, res) { const sources = await supabase.from('raw_feeds')... const brief = await gemini.summarize(sources); await slack.post(brief); }
💡 학습 포인트: 단일 도구에 종속되지 않고 "각자의 강점에 일을 맡기는" 사고방식. 이게 진짜 엔지니어링 감각이다.

CASE C

🚀 아이디어 검증기
Idea Validator

30초 안에 시장성·경쟁·MVP 범위·예상 리스크를 리턴.

SKILL DESIGN

EVOLUTION

개인 도구에서 상품까지

  1. 본인이 매일 쓴다
    최소 4주, 실제 자동화 루프에 편입된 상태
  2. 측정 지표를 만든다
    절약 시간, 발견한 이슈 건수, 의사결정 가속 정도
  3. 주변 1~3명에게 무료 베타
    동일 페인 포인트를 가진 사람을 찾는 단계
  4. 가격 구조 실험
    월 구독, 사용량 과금, 일회성 등 가설 검증
  5. 제품화 분기점 판단
    MRR 30만원이 1차 게이트, 100만원이 본격 분기
CHECKLIST

3개월 이내 달성 목표

  • 최소 1개의 스킬을 100회 이상 실제로 사용해봤다
  • 그 스킬을 에이전트로 옮겨 Slack 자동화 루프에 편입했다
  • 실행 로그가 Supabase에 누적되어 있고 조회 가능하다
  • "누군가 돈 내고 쓸 수 있을까?" 답을 명확하게 안다
  • 다음 분기 동안 검증할 가설을 1개 이상 정해뒀다
