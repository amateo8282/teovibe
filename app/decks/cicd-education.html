CONCEPT 01

CI — 지속적 통합

Continuous Integration.
코드를 저장소에 push할 때마다 자동으로 빌드·테스트를 실행하는 것.

핵심 질문: "내 코드가 기존 코드를 안 깨뜨렸나?"

💡 CI가 없으면? → push하고 나서 "어, 테스트 왜 깨지지?" 를 수동으로 발견. 팀이 클수록 지옥.
CONCEPT 02

CD — 지속적 배포

📦 Continuous Delivery

  • 배포 준비까지 자동
  • 실제 배포는 사람이 버튼 클릭
  • "준비는 됐어, 네가 눌러"

🚀 Continuous Deployment

  • 테스트 통과 → 서버 배포까지 전자동
  • 사람 개입 없음
  • "push했더니 이미 배포됨"
💡 둘 다 "CD"라고 부름. 보통 팀에서 "CI/CD 있어요" 하면 Deployment 쪽을 의미.

COMPARE

1인 로컬 서버 vs 팀 개발

🏠 내 셋업 (1인 iMac)

  • 소스 = 런타임 = 같은 iMac
  • SSH 편집 = 즉시 배포
  • 깨진 코드 = 나만 피해
  • 팀 충돌 없음
  • GitHub = 백업 용도

👥 일반 팀 개발

  • 여러 명이 같은 코드를 수정
  • 내 코드가 남의 코드를 깰 수 있음
  • 서버가 원격 (배포 자동화 필요)
  • merge 전 검증 필수
  • CI/CD 없으면 혼돈
KEY INSIGHT

1인 로컬 서버에서
CI/CD가 필요 없는 이유

  • 배포가 이미 즉각적 — SSH 편집 = 그 자체가 배포. 파이프라인 불필요.
  • 테스트 대상이 나 혼자 — "남의 코드를 깨뜨릴" 상황 자체가 없음.
  • LaunchAgent가 운영을 담당 — 서비스 재시작·스케줄·헬스체크는 따로 해결됨.
  • 오버엔지니어링 — GitHub Actions 셋업 비용 > 얻는 이득.
