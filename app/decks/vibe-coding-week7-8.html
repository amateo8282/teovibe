CONCEPT 01

엔티티(Entity)란?

엔티티는 한마디로 "우리가 관심을 갖고 데이터를 저장하고 싶은 것"입니다.

현실 세계에서 구별 가능한 사물, 개념, 사건 — 이것들을 소프트웨어 세계로 옮겨 놓은 것이 엔티티입니다.

💡 핵심: 엔티티 = "식별 가능하고, 속성을 가지며, 시간이 지나도 동일성을 유지하는 것"
REAL WORLD

일상 속 엔티티 찾기

👤

이름, 이메일, 가입일이라는 속성을 가진 "사람"

📦

주문번호, 금액, 상태를 가진 "거래 사건"

💄

화장품

브랜드, 카테고리, 가격을 가진 "상품"

💡 이름을 바꿔도 같은 사람, 가격이 바뀌어도 같은 상품 → "고유 식별자(ID)"가 동일성을 보장

PART 1

데이터베이스
엔티티

"저장해야 할 것"을 정의하는 전통적 관점

DEFINITION

DB에서의 엔티티

데이터베이스에서 엔티티란 데이터를 저장할 단위입니다.
쉽게 말해, 테이블 하나 = 엔티티 하나라고 생각하면 됩니다.

  • 엔티티 이름 — 테이블명 (예: User, Product, Order)
  • 속성(Attribute) — 컬럼 (예: name, email, price)
  • 인스턴스 — 행(Row), 실제 데이터 한 건
  • 관계(Relationship) — 테이블 간 연결 (1:N, N:M)
EXAMPLE

쇼핑몰 ERD 예시

User Order Product ────────── ────────── ────────── id (PK) id (PK) id (PK) name user_id (FK) name email total price created_at status category User 1 ──── N Order N ──── M Product
💡 엔티티 식별 팁: "○○을/를 관리해야 해" → ○○이 엔티티 후보!
"회원을 관리해야 해" → User 엔티티, "주문을 관리해야 해" → Order 엔티티
KEY DISTINCTION

엔티티 vs 값 객체(VO)

🔑 엔티티 (Entity)

  • 고유 ID로 식별
  • 속성이 바뀌어도 같은 객체
  • 생명주기가 있음 (생성→변경→삭제)
  • 예: 사용자, 주문, 계좌

📐 값 객체 (Value Object)

  • 값 자체로 식별 (ID 없음)
  • 값이 바뀌면 다른 객체
  • 불변(immutable)
  • 예: 주소, 금액, 이메일
💡 "김철수"가 이사를 해도 같은 사람 → 엔티티
"서울시 강남구" → "부산시 해운대구"로 바뀌면 다른 주소 → 값 객체

CONCEPT 02

클린 아키텍처란?

로버트 C. 마틴(Uncle Bob)이 제안한 소프트웨어 설계 철학입니다.
핵심 아이디어: "비즈니스 규칙을 외부 기술로부터 보호하라"

🌐 프레임워크 & 드라이버 웹, DB, UI (가장 바깥)
↕
🔌 인터페이스 어댑터 컨트롤러, 프레젠터, 게이트웨이
↕
⚙️ 유스케이스 애플리케이션 비즈니스 규칙
↕
🧩 엔티티 핵심 비즈니스 규칙 (가장 안쪽)
CORE RULE

의존성 규칙
(Dependency Rule)

클린 아키텍처의 유일하고 절대적인 규칙:

🎯 바깥 원 → 안쪽 원으로만 의존할 수 있다
안쪽 원은 바깥 원의 존재를 절대 모른다

✅ 올바른 방향

Controller → UseCase → Entity
DB Repository → Entity

❌ 위반하는 방향

Entity → DB 라이브러리
Entity → HTTP 프레임워크

DEEP DIVE

클린 아키텍처의 엔티티는
DB 엔티티와 다르다

🗄️ DB 엔티티

  • 데이터 저장 구조
  • 테이블 스키마에 종속
  • CRUD 중심
  • "어떻게 저장할까?"

🏛️ 클린 엔티티

  • 비즈니스 규칙을 캡슐화
  • 어떤 기술에도 종속 안 됨
  • 행위(메서드) 중심
  • "이 도메인의 규칙은 뭘까?"
CODE EXAMPLE

코드로 보는 차이

❌ DB에 종속된 엔티티

// Supabase 테이블 그대로 매핑 type User = { id: string // uuid name: string email: string created_at: Date } // 규칙이 없다! 그냥 데이터 덩어리

✅ 클린 엔티티

class User { constructor( readonly id: UserId, private name: string, private email: Email, ) {} changeName(newName: string) { // ✅ 비즈니스 규칙 포함! if (newName.length < 2) throw '이름은 2자 이상' this.name = newName; } }
WHY IT MATTERS

왜 엔티티가 중심에 있을까?

  • 가장 안정적: 비즈니스 본질은 잘 안 바뀜. DB나 프레임워크보다 수명이 긺
  • 기술 독립: Supabase → Firebase로 바꿔도 엔티티는 안 바뀜
  • 테스트 용이: DB, 네트워크 없이 비즈니스 규칙만 단독 테스트 가능
  • 공유 가능: 같은 엔티티를 웹, 앱, API에서 재사용
💡 비유: 엔티티 = 건물의 "설계도"
벽돌을 바꾸든(DB), 인테리어를 바꾸든(UI), 설계도의 구조는 그대로
PART 3

온톨로지와
엔티티

"세상을 어떻게 분류할 것인가"
— 그리고 왜 AI 시대에 이것이 중요한가

CONCEPT

온톨로지(Ontology)란?

원래 철학에서 "존재론" — "존재하는 것은 무엇인가?"를 탐구하는 학문입니다.

컴퓨터 과학에서는 "특정 도메인의 개념, 분류, 관계를 형식적으로 정의하는 체계"가 되었습니다.

쉽게 말해, 엔티티가 "무엇"이라면
온톨로지는 그것들의 "지도"입니다.

💡 비유: 도서관의 "분류 체계"가 온톨로지.
각 책(=엔티티)이 어떤 카테고리에 속하고, 어떤 관계가 있는지를 정의한 시스템
RELATIONSHIP

온톨로지 → 엔티티 → 속성

온톨로지는 엔티티의 "상위 설계도"입니다.
구체화의 순서를 따라가 봅시다.

🌐

온톨로지

"화장품 세계에는
브랜드·제품·성분·
피부타입이 있다"

→
🧩

관리한다"

→
📋

💡 온톨로지 = 세계관 / 엔티티 = 세계관 안의 등장인물 / 속성 = 등장인물의 프로필
WHY NOW

왜 AI 시대에
온톨로지가 중요한가?

🤖

AI는 "맥락"이 필요하다

ChatGPT, Claude 같은 LLM은 도메인의 구조를 알려줘야 정확한 코드를 생성합니다. 온톨로지적 설명 = AI에게 주는 "세계 설정집"

🔗

지식 그래프의 기반

구글 검색, 시리, AEO — 모두 온톨로지 기반의 지식 그래프 위에서 작동합니다. 엔티티 간 관계를 아는 것이 AI의 핵심

📐

DDD의 유비쿼터스 언어

팀원 모두가 같은 용어 체계를 쓰는 것 = 미니 온톨로지를 공유하는 것. AI도 이 언어를 써야 합니다

🎯

프롬프트의 정밀도

엔티티만 나열하면 "무엇"만 전달. 온톨로지적 사고를 더하면 "왜 이렇게 연결되는지"까지 전달 가능

EXAMPLE

온톨로지적 사고로
프롬프트 업그레이드

❌ 엔티티만 나열

  • "User, Product, Order
    테이블 만들어줘"
  • → AI가 관계를 추측
  • → 규칙 없는 CRUD만 생성
  • → 도메인 특성 반영 안 됨

✅ 온톨로지적 설명 추가

  • "User는 Buyer 또는 Seller 역할"
  • "Product는 반드시 1개 이상의 Ingredient를 포함"
  • "Ingredient는 SkinType과 적합/부적합 관계"
  • → AI가 제약 조건과 관계 구조까지 이해
💡 핵심: AI에게 "무엇이 있다"만이 아니라 "어떻게 연결되고, 어떤 규칙이 있다"를 알려줘야 좋은 코드가 나온다

CONCEPT 04

바이브코딩에서의 엔티티
= 문제 정의의 단위

바이브코딩은 AI에게 프롬프트로 코드를 짜게 합니다.
이때 가장 중요한 건 "무엇을 만들 것인가"를 정확히 정의하는 것입니다.

엔티티를 먼저 정의하면:

  • AI가 테이블 구조를 알아서 설계한다
  • AI가 API 엔드포인트를 자동으로 만든다
  • AI가 UI 폼을 엔티티 속성 기반으로 생성한다
  • 팀원과 공통 언어로 소통할 수 있다 (유비쿼터스 언어)
COMPARE

프롬프트 품질의 차이

❌ 엔티티 없이

  • "쇼핑몰 사이트 만들어줘"
  • "회원가입이랑 상품 보여주는 거"
  • "결제도 되게 해줘"
  • → AI가 추측으로 설계 😵

✅ 엔티티 먼저 정의

  • "User: id, email, role(buyer|seller)"
  • "Product: id, name, price, seller_id"
  • "Order: id, buyer_id, items[], status"
  • → AI가 정확하게 설계 🎯

CHECKLIST

좋은 엔티티 정의 체크리스트

  • 식별 가능한가? — 고유 ID가 있는가?
  • 속성이 있는가? — 최소 2~3개의 의미 있는 속성이 있는가?
  • 생명주기가 있는가? — 생성, 변경, 삭제가 되는가?
  • 비즈니스 규칙이 있는가? — "반드시 ~해야 한다"는 조건이 있는가?
  • 관계가 있는가? — 다른 엔티티와 연결되는가?
  • 이름이 명확한가? — 팀원 누구나 같은 의미로 이해하는가?
COMMON MISTAKES

초보자가 자주 하는 실수

🚫

엔티티 = 테이블로만 생각

DB 컬럼에만 집중하고 비즈니스 규칙을 빼먹음. "가격은 0보다 커야 한다" 같은 규칙이 코드 여기저기 흩어짐

🚫

엔티티를 너무 많이 만듦

"배송지"를 별도 엔티티로? 값 객체로 충분한 걸 엔티티로 만들면 복잡성만 증가

🚫

엔티티에 UI 로직 넣기

"버튼 색상", "정렬 순서" 같은 UI 관심사를 엔티티에 넣으면 클린 아키텍처 위반
